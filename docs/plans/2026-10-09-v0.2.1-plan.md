  - "新增通用扩展负载重排能力"：**不需要**（进程内固定即真机行为，预设照抄合法）；
  - "升序为规范形并钉死预设"：**不成立**（不是升序）；
  - **撤回**旧计划里的"全预设剔除 51764"——真 Chrome 就发它，剔了反而与真机不符。
- 想让某个会话不带 51764（或改其载荷）：用 **`profile_patch`**（T-J2 运行时增量覆盖）
  ——已实测：patch 后线上回显不含 51764，JA4 从 `…1517h2_…cb7bf5808d99` 变为

## T-I 创宇盾案例：HTTP identity 兜底（最终定案，2026-10-14 晚）

### 背景

工信部 ICP 接口（hlwicpfwc.miit.gov.cn，前有**创宇盾/加速乐云 WAF**，特征头
`X-Via-Jsl` + 拦截页 `365cyd.com`）：curl_cffi 可过、geektls 403。用户反馈
"TLS 各方面远超 curl_cffi 但效果反而不如"。

### 定案一（query 端点 403 的直接根因，2026-10-14 晚·业务脚本实测）

**创宇盾对 `queryByCondition` 端点的"精准访问控制"（PAC）校验请求 body 的
字节格式**：绑定层 `json=` 参数若用平台默认序列化（Python：分隔符 `", "`/`": "`
带空格），与浏览器 `JSON.stringify` 的**紧凑格式**
（`separators=(",", ":")`）不符，被判为非浏览器客户端 → 403。

- 决定性证据：同一 preset 会话、同一业务流，仅把 query body 从 `json=` 换成
  紧凑 `data=` 字节 → **403 变 200**（`{"code":200,"msg":"操作成功"}`）；
  `qq.com` 实测取数成功（深圳市腾讯计算机系统有限公司 粤B2-20090059-5）。
- 解释"auth 过、验证码过、仅 query 挂"：WAF 规则只作用于 query 端点；auth 用
  表单编码（两库一致），故不受影响。
- 重要：**"CH 复刻 / 头集合 / Cookie / 帧层"全部对齐仍 403 的原因就在于此**
  ——判点根本不在 TLS 层，此前所有 TLS 侧的排查方向（含本段下方的定案二实验）
  都绕过了真正的判点。
- 修复：见 T-I4b（业务侧已实证；绑定层默认行为待改）。

### 定案二（低层装载的 identity 缺失——另一独立真缺陷，主页实验）

**真根因：低层装载入口（`clienthello_hex=` / `ja3=` / `ja4r=` / 无 identity 的
自定义 detail）不携带 HTTP identity（浏览器头套件）**，引擎的身份注入
（`engine/roundtrip.go` 的 `applyIdentity`）无事可做，请求头退化为 **Go 默认
（`User-Agent: Go-http-client/2.0` + 仅 4 头）**，被创宇盾"精准访问控制"
（拦截页 `error_403_type:"pac"`）按"程序化 UA / 缺浏览器特征头"直接拦截（403）。

**关键实验证据**（同环境、同目标、受控可复现；脚本 exp5/8/9/10/11/12）：

| 臂 | TLS 层 | 实际 HTTP 头 | 结果 |
|---|---|---|---|
| curl_cffi chrome | 基线 | 全套 15 头（Chrome 150 mac） | 404 放行 |
| preset / profile= | 每次洗牌 | identity 注入 15 头（Chrome 154 win） | 404 放行 |
| preset + 固定 curl 顺序（D 臂） | curl 序、关洗牌 | 15 头 | 404 放行 |
| clienthello_hex（curl 逐字节复刻） | 完美（除随机项全对齐） | **Go-http-client/2.0，仅 4 头** | **403 拦截** |
| hex + 显式全套 identity 头 | 同上 | 15 头 | **404 放行** |
| hex + 仅 UA（User-Agent 一项） | 同上 | UA 正确 | **404 放行** |

- 抓包佐证：hex 的第二 flight 应用数据仅 149B（裸头），D/preset 为 767B（全套头）；
  httpbin 回显：hex 会话 `headers count: 4`（`User-Agent: Go-http-client/2.0`），
  preset/D `headers count: 15`（UA=Chrome/154 + sec-ch-ua* + Sec-Fetch-* 等）。
- 业务进程 403 同因：业务代码走 hex/无 identity 路径且不主动设 UA ⇒ Go 默认 UA ⇒ PAC 拦截。

### 被推翻的旧"定案"（2026-10-14 上午，观测受业务进程并发污染）

- **扩展顺序"头号根因"：错误**。D 臂（固定 curl 序 + 关洗牌）404 放行；preset 的
  随机洗牌序同样放行 ⇒ WAF 不校验扩展顺序。
- **ECH GREASE 长度 218 vs 282：非缺陷**。两者均为 Chrome 候选集 {144,176,208,240}
  (+42) 内的随机选择；A 臂（hex 改 282）仍 403。
- **sig_algs 带 GREASE：非拦点**。D 臂带 GREASE 放行；真 Chrome/BoringSSL 也带
  GREASE（curl-impersonate 未开而已）——不应"移除"，如需对齐按目标基准定。
- **GREASE 载荷"首 0 尾 1"：本就一致**（exp9 抓包 diff：两边均首 0 字节、尾 1 字节）。
- **TCP 分段 / CCS / flight 结构：两边一致**（1448+321、80、24）——T-I2 降级。
- **CH 字节层面：hex 路径可 100% 复刻 curl**（18 扩展逐项：顺序/长度/载荷全同，
  仅 random/sid/key_share 密钥/GREASE 值不同——真浏览器同样每次随机）。归一化掩码
  diff（analyze_diff.py）显示 hex(403) vs D(404) 仅剩 sig_algs GREASE 一处差异。
- **TLS 栈/记录层/TCP 栈特征也排除**（2026-10-14 晚）：同一会话内 auth(200) 与
  query(403) 的 TLS/连接完全相同，唯一差异是 query 的 body 格式；body 改紧凑后
  即 200。此前"Go 的 TLS 记录层/TCP 栈与真实 Chrome 存在系统性差异"的判断不再成立
  （同机同栈的 curl 侧仅凭 body 格式即可解释全部现象）。

## T-K multipart/form-data 上传 ✅ 已实施（2026-10-14，Python 绑定）

- 形态（用户 2026-10-14 指示实施）：**构造器 + 请求级参数**——
  - `Multipart`：`add_part(name, *, data=/local_path=, filename=, content_type=)`
    （`local_path`/`data` 二选一）、`from_list([{...}, …])`、可选 `close()`；
    同名 part 可重复（同字段多文件）；`s.post(url, multipart=mp)` 发起；
  - `data=` 的 dict / 元组列表作为普通字段**尾随**并入表单；与 `json=`、
    `data=`（字符串/字节/可迭代）互斥（报错，不静默降级）；
  - boundary 为**浏览器形态**（`----WebKitFormBoundary` + 16 位随机；分隔行 `--` + boundary，
    不跟随任何库的形态）；`content-type` 由构造器接管，`content_type` 显式优先、未给按
    文件名扩展名推断（推断不出用 `application/octet-stream`，纯字段不带该头）。
- 落点：**Python 绑定层**（渲染 body 字节走既有 `body_b64` 通道）——**零引擎/FFI 改动**。
- 验证（2026-10-14）：httpbin `/post` 回显对拍（form/files/同名字段/中文/content-type
  与等价调用结构一致）+ 原始字节级断言（4 part → 5 处分隔行、`name="image"`×2、
  `Content-Type` 透传）+ 互斥/缺文件/空 part 边界用例——全绿。
- 边界（如实）：文件整块读入内存（大文件流式 = 后续项，可复用既有 chunked 上传通道）；
  Node/Go 绑定未同步（待定）；`files=` 便捷参数**不做**（构造器语义已足够直观，
  多值/多文件/类型一目了然）。

### L-5 pcapng 多接口（多 IDB）只取第一个链路类型

- 现象：`core/pcapimport/pcapimport.go:473` 的守卫 `linkType == -1` 使
  `parsePcapng` **只记录第一个 IDB 的链路类型**，随后 `:476` 的 EPB/PB 分支用这一个
  值去解析**全部**包；而 EPB 的接口号（`body[0:4]`）与 PB 的接口号（`body[0:2]`）
  从头到尾没有被读取。
- 影响：多网卡/多接口合并的 pcapng（如 `tcpdump -i any` 之外的多路合并、镜像口导出）
  中，来自接口 1 及以后的包会按接口 0 的链路类型解析 ⇒ 静默丢弃或误解析。
  单接口抓包（当前 T-F 的主场景）不受影响。
- 建议：维护 `[]int` 的 iface→linkType 表，按每个 EPB/PB 的 interface id 取对应类型；
  越界的 interface id 记入 `Skipped`。属健壮性补强，不阻塞当前用法。

### L-6 Node 绑定的库名选择不看 CPU 架构

- 现象：`bindings/nodejs/index.js:22-31` 的 `libNames()` 只 `switch (process.platform)`，

  `libgeektls.dylib`，而发布流水线只产 arm64 那一份。
- 影响：Intel Mac 上加载失败，报错是 `cannot load the geektls core library; set
  GEEDTLS_LIB to its path. Tried: …`——指向"设环境变量"，但对"架构不匹配"这个真实原因
  没有任何提示。README 已如实标注"Intel Mac 暂不支持"，但失败形态与标注不匹配。
- 建议：`libNames()` 在 darwin 分支按 `process.arch` 分派（arm64 → `libgeektls.dylib`，
  x64 → `libgeektls-x64.dylib`），并在架构不支持时抛出**明确的**平台不支持错误，
  而不是让 koffi 的加载失败兜底。
