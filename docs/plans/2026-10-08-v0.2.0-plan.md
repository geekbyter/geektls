### T1.1 Firefox / Safari 的 H3 采集（v0.1.9 T5.3 顺延；优先级最高）

- 现状：`tests/e2e/e1_h3_test.go` 的 **Firefox 适配已完成**（`-headless -profile`
  + 官方测试 pref `network.http.http3.alt-svc-mapping-for-testing`，值格式按 Firefox
  源码修正为 `host;h3=:port`；WSL→Windows 路径处理 + 可写性探测）。**本机 WSL 实测
  未走 QUIC**（TCP 连上、UDP 无 Initial；Chrome 对照实验未跑，未最终归因——疑
  WSL→Windows 浏览器的 UDP/pref 环境问题，非代码问题）。
- 做法：① 在 **Windows 原生跑 Go**（`go test` 直接在 Windows 侧）或非 WSL 环境重试；
  ② 若仍不通，先跑 Chrome 对照实验（路径已备）定位"WSL UDP 转发 vs Firefox pref"；
  ③ 拿到记录后按实测补预设 `http3` 节（firefox_157 优先；Safari 同理）。
- 判据：`h3_firefox_*` 证据记录落 `profiles/evidence/browsers/` + 对应预设 http3 节。
- 连带：T2.4 的 `settings_order_values` / `pseudo_header_order` 升 E2（依赖本条）。

### T1.2 扩展 51764 的负载子项顺序判定（v0.1.9 T5.2 顺延）

- 现状：chrome_152_macos（E3 素材）乱序、chrome_154 三平台升序且逐字节相同——
  **每连接随机 vs 固定未定论**。
- 做法：本机 Chrome（≥152）对 peet.ws **双抓**（同版本两次），比对 51764 负载字节序。
- 分支：随机 ⇒ 新增"通用扩展负载重排"能力（仿 `extension_permutation`）；
  固定 ⇒ 以升序为规范形并在预设里钉死。
- 判据：判定后落一项（能力或预设规范形）。

## P2 — 能力与工程（无样本也可推进）

### T2.1 ja4plus 离线交叉验收（v0.1.9 T1.3 顺延）

- 需外部 CLI（`ja4plus analyze capture.pcap --types ja4`）；形态：人工/夜间跑，
  **不进任何依赖树**；只碰 JA4 本体（FoxIO 其余方法不碰，见"明确不做"）。
- 判据：同一 pcap 的 JA4 与我方 `check_profile`/selfcheck 逐字符交叉一致。

### T2.2 keylog 解密支线评估（v0.1.9 T1.4）

- 先评估 tshark 解密输出的稳定性（字段齐全度/多版本）再排期；目标是补 **H2 面**
  导入（SETTINGS/WINDOW_UPDATE/伪头序）——即 `pseudo_header_order` 的 E4 空位。

### T2.3 H3 残余证据项（v0.1.9 T2.3/T2.4 顺延）

- `h3.quic_grease_frames` 的 **E2 真机控制流对拍**（现 E1 只到 QUIC 握手层）。
- 私有 transport params `0x11`/`0x3128` 的 blob 落库（blob 与连接级参数冲突待
  fork 决策）。

### T2.4 docs/08 §E 同族缺口 59 条的处置说明（非行动项，如实登记）

- 59 条 = PSK 变体 15（按约定跳过）+ 无 spec 工厂 27（上游自身不可提取，
  `please implement this method`）+ 可提取若干（chrome 系全部带 `≈` 平台后缀命中，
  实为命名差异非真缺口）。**保持现状**；仅当上游换实现/新增族时重跑提取器
  `go run ./cmd/import-tlsclient`。
